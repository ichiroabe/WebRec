# Web作業とローカル作業のシームレス化（構想メモ）

2026-08-30 時点の検討内容。まだ実装方針は確定していない。

## やりたいこと

Web上の作業と、手元のPCでの作業（ファイル・Excel・DB）を、人が間に入らずに
つなげたい。

```
ローカルで下ごしらえ → Webで入力・取得 → その結果をまたローカルで処理
```

## 構想

WebRec で記録した JSON を MCP サーバー経由で公開し、**Claude Cowork を進行役**にする。

```
┌─────────────────────────────────────────────┐
│ Claude Cowork（進行役）                      │
│   ・ローカル作業（ファイル / Excel / DB）      │
│   ・どの手順をどの順で呼ぶか判断              │
└───────────────┬─────────────────────────────┘
                │ MCP
┌───────────────▼─────────────────────────────┐
│ WebRec の録画JSON（手順の実体）               │
│   ・記録済み・検証済みの決まった手順           │
│   ・{{data.列名}} が引数                      │
└─────────────────────────────────────────────┘
```

### この形の要点

**LLM にブラウザを手探りで操作させない。** Claude は「録って検証済みの手順を呼ぶ」
だけで、要素を探して押す判断はしない。業務システム相手ではここが決定的に効く。

- 再現性が保てる（毎回同じ手順が走る）
- 事前に検証できる（壊れた手順は保存段階で弾かれる）
- 取り違えが起きにくい

Claude が担うのは「順番の判断」と「ローカル作業」であって、画面操作そのものではない。

## 実行方式の候補

録画JSONを実際に動かす手段が2つある。**どちらに決めても、後述の準備は無駄にならない。**

| | Claude in Chrome | Playwright |
| --- | --- | --- |
| ログイン状態 | **実ブラウザのまま使える** | 専用プロファイルが要る（初回に手でログイン） |
| 導入 | **追加インストール不要** | Playwright の導入が必要 |
| 決定性 | 実行器をそのまま流すので同等 | 同等 |
| iframe / frameset | `javascript_tool` の対象フレームに制約 | 全フレームに注入できる |
| 速度 | ページ遷移ごとに Claude が介在 | 一気に走る |
| **無人実行**（スケジュール・CI） | **不可**（Claude のセッションが要る） | **可** |

### Claude in Chrome 方式が有利な理由

普段使いの Chrome をそのまま使うため、**ログイン・セッションの問題が消える**。
Playwright は起動中の Chrome プロファイルを開けないので、専用プロファイルを用意して
初回に手でログインする手間が要る。

対話的に進める用途（Cowork はまさにこれ）では Claude in Chrome の方が素直。
無人で定期実行したい場合のみ Playwright が必要になる。

### Claude が介在する回数を抑える

1ステップずつ往復するとコストも時間もかかる。**ページ遷移が起きるまでを1回の
JavaScript にまとめて流す**のが現実的。ページが遷移すると注入したスクリプトは
死ぬので、そこで一度 Claude に戻り、次の塊を流す。

50ステップの録画でも、遷移が3回なら往復4回で済む。

MCP サーバーは「次に実行すべき塊」を返す役に徹する。

```
list_recordings()          どんな自動化があるか
describe(name)             何をするか / 必要な入力
next_chunk(name, state)    次に流す JavaScript と、実行後の状態
```

## 既にあるもの（確認済み）

| 必要なもの | 状況 |
| --- | --- |
| 手順の実体 | 録画JSONそのもの。エクスポート時はアップロードしたファイルの中身も埋め込まれる |
| 引数の受け口 | `{{data.列名}}` がそのまま引数になる |
| 引数の自動抽出 | `validate.js` が参照中の列を集めている（`referencedColumns`）ので流用できる |
| 事前検証 | `parseRecordingJson` と `validateRecording` で壊れた手順を弾ける |
| 実行結果 | ステップごとの成否・失敗理由（実行ログ） |
| **実行器の可搬性** | `performStepInPage`（background.js）は**約400行の完全に自己完結した関数**で、外部変数を一切参照していない。`chrome.scripting` からでも `javascript_tool` からでも Playwright からでも、そのまま流せる |

最後の項目が効く。実行方式を決める前から、中核の資産は保全されている。

## 足りないもの

### 1. 値を取り出すステップ（最優先・必須）

現状 `assertText`（照合）はあるが、**ページから値を取り出して返す手段が無い**。
Claude に返せるのは成否だけで、「Webから取得 → ローカルで処理」の向きが成立しない。

```json
{ "type": "extract", "selector": "#total", "as": "合計金額" }
{ "type": "extractTable", "selector": "#result", "as": "明細" }
```

これで戻り値が `{ 合計金額: "12,340", 明細: [...] }` になり、そのままローカル処理へ渡せる。

**実行方式をどちらに決めても必要になる。**

### 2. 録画の説明欄

Claude が「どれを呼ぶべきか」を判断するには名前だけでは足りない。`description` を
持たせ、MCP ツールの説明文に流す。

### 3. 実行器の切り出し

`performStepInPage` を `src/executor.js` へ移し、拡張機能・Claude in Chrome・
Playwright のどこからでも同じものを使えるようにする。純粋な整理で、拡張機能の
動作は変わらない。

### 4. MCP サーバー

3 ができれば薄い。

## 詰めておくべき点

- **取り返しのつかない操作** … MCP 経由で送信や削除ができてしまう。録画に「破壊的」
  フラグを持たせ、Claude が呼ぶ前に確認を挟む設計にすべき
- **同時実行** … ブラウザは1本ずつ（拡張機能側には `replayBusy` のガードがある）
- **iframe / frameset** … Claude in Chrome 方式では対象フレームの扱いに制約がある。
  frameset を使う画面を自動化する場合は要確認

## 未確認事項

- **Cowork で Claude in Chrome のツールが使えるか。** 開発時のセッションでは使えて
  いたが、Cowork 環境で同じツールが提供されるかは環境側の設定次第。**実際に試して
  確認する必要がある**
- 使えない場合は Playwright 方式に倒すことになるが、実行器を切り出しておけば
  どちらでも同じものを呼べる

## 進め方の案

```
1. extract / extractTable ステップを追加     ← Web→ローカルの向きに必須
2. 録画に description を追加                 ← 小さい
3. performStepInPage を executor.js へ切り出し ← 純粋な整理
4. MCP サーバー
```

1〜3 は実行方式が未定でも着手できる。並行して、Cowork で Claude in Chrome が
使えるかを確認するのが良い。

Playwright 方式に進む場合は、3 のあとに CLI ランナーを作る。**その時点で既に
価値がある**（タスクスケジューラから叩ける）。MCP サーバーはその上に薄く載せる。
